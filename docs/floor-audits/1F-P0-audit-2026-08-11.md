## 1. 结论摘要

1F 的建筑壳体、卧室冻结方案、双壁龛媒体墙和“左下 B1、右上 2F”楼梯逻辑已经进入可追溯状态；现行修订号也与本轮指定版本一致。

但目前不能直接进入施工深化或把十张写实图视为“严格模型输出”，原因有三项 P0：

1. 餐桌与 2400mm 水吧在当前坐标上发生真实碰撞，展开态也没有独立的 2D/3D 几何状态。
2. U 形厨房标准台面段约有 926mm，但独立冰箱段只有约 755–770mm，未达到本轮要求的 900mm。
3. 水吧给排水、客卫防水范围与排水坡度仍只有需求元数据，没有施工路径和节点；不能据此下单或开槽。

01、08、10号交付图的主要问题属于摄影机与可见性问题：写实图已经人为修正构图，但当前模型保存的机位仍会近距离遮挡或穿透，因此“效果图可看”不等于“3D机位已收敛”。

## 3. 问题清单

### P0-01 餐桌与水吧真实碰撞，展开方案不可实施

- 分类：真实冲突 / 模型逻辑问题
- 影响对象：`module-1f-table-001`、`furn-living-waterbar-001`、`furn-living-waterbar-upper-001`、`L-1F-V1-33`
- 证据：闭合1550mm桌面已与水吧前沿交叠约24mm；2700mm套组包络与水吧交叠550×2400mm；2400×1200展开态无论横竖均无法获得餐椅后退和水吧操作通道。
- 根因：餐桌尺寸字段同时承担“整套餐桌椅包络”，3D又按该字段的58%/54%绘制闭合桌面；`expandedSizeCm`只是描述参数，没有独立状态几何。当前落位也未为水吧操作面留通道。
- 建议修法：先冻结周末展开时的长轴方向和扩容流程；随后在1F数据中建立 `closed` / `expanded` 两套可校核包络，重排桌心或缩减/移位水吧。不得只靠效果图缩小家具。
- 预计改动文件：1F专属迁移脚本、`data/default-workspace.json`；若现有状态模型不支持双包络，再由主任务裁决是否扩展共享家具状态接口；同步更新餐桌吊灯点位与十机位产物。
- 验收测试：新增 `scripts/test-1f-p0-clearances.mjs`，分别断言闭合桌、水吧操作面、厨房入口连续通道和展开态8–10座椅包络；运行 `test-furniture-placement`、`test-object-sync`、`test-render-preflight`、`test-lighting-design`。

### P0-02 冰箱段净宽不足900mm，开门与抽屉操作未闭环

- 分类：真实冲突 / 模型逻辑问题
- 影响对象：`furn-fridge-001`、`furn-kitchen-u-left-run`、`furn-cooktop-001`、`furn-kitchen-u-right-run`
- 证据：西侧柜前沿x=6095，冰箱前沿x=6850，净宽约755mm；现有操作校核给出约770mm，均低于900mm。冰箱完全开门和抽屉拉出时会进一步占用该净宽。
- 根因：2298mm房宽中同时放置550mm西侧柜、700mm深冰箱及较大的冰箱后部预留，现有坐标无法满足目标净宽。
- 建议修法：先按实际冰箱SKU确认机身深度、门体突出、铰链侧和90°/120°开启要求；优先选薄机身或调整冰箱朝向/位置，再微调西侧柜尾端。不得通过删掉冰箱开门动画“解决”。
- 预计改动文件：1F专属迁移脚本、`data/default-workspace.json`、厨房设备选型表；如只改对象参数，不应修改共享渲染器。
- 验收测试：新增冰箱实体包络、90°门扇包络、抽屉完全拉出和最窄通行带断言；运行 `test-furniture-placement`、`test-render-preflight`。

### P0-03 水吧给排水路径未建立

- 分类：现场待复尺 / 机电深化缺口
- 影响对象：`furn-living-waterbar-001`、`W-1F-011`、相邻客卫与厨房排水系统
- 证据：水吧只记录 `hotCold + wallDrain` 需求，没有给水点、排水点、管径、坡度、立管、穿墙/穿楼板或检修口数据。水吧北端至客卫南边界沿同一东墙约2.75m，原则上可借湿区，但尚未证明结构层和完成面能容纳重力排水。
- 建议修法：现场确认东墙可走管范围、最近排水立管、楼板开孔权限和地面构造厚度；按约2.75–3.3m路线复核排水坡降。若无法做可靠重力排水，冻结为干吧/净饮上水方案，或采用经确认的提升排水设备并设置可检修、防噪和防返水措施。
- 预计改动文件：1F给排水深化数据/图纸、1F专属迁移脚本、`data/default-workspace.json`；不应改共享材质与灯光体系。
- 验收测试：水吧必须具备可追溯水源、排水终点、管径、坡度/设备和检修空间；施工包预检不得仅凭 `needsDrainage=true` 判定通过。

### P0-04 客卫防水与排水施工信息缺失

- 分类：施工深化缺口 / 现场待复尺
- 影响对象：`ROOM-1F-003`、`furn-bath-shower-001`、`furn-bath-toilet-001`、`furn-bath-vanity-001`、`D-1F-005`、`WIN-1F-002`
- 证据：当前仅有防滑砖、防水墙面材质和 `waterproofRequired` 标记；没有淋浴/干区防水边界、墙面上翻高度、门槛止水、地漏位置、坡向、管根加强和闭水试验要求。
- 建议修法：补一张1814×2700mm湿区深化图，明确淋浴区和干区的防水范围、两道排水或单地漏方案、坡度、门槛与窗台防水收口；淋浴内窗需确认型材、玻璃和窗台排水节点。
- 预计改动文件：1F防水/给排水深化数据、施工图输出配置、`data/default-workspace.json`中的1F专属图纸对象。
- 验收测试：防水多边形覆盖、门口止水、地漏坡向、窗台节点和闭水试验字段齐全；运行施工包预检与引用校验。

### P1-01 东侧操作台“含同宽吊柜”只存在于文字，当前3D未形成可靠独立几何

- 分类：3D美化/模型表达问题
- 影响对象：`furn-kitchen-u-right-run`
- 证据：对象名和施工说明要求900mm地柜加同宽吊柜，但对象高度只有900mm、variant=`baseCabinet`，没有独立上柜对象或明确的上柜子件；当前模型截图中上柜表达不稳定，写实图则人为补齐。
- 建议修法：在1F对象层增加受同一父柜控制的吊柜子件或柜体分层参数，绑定同一坐标和材质，不要依赖提示词补画。
- 预计改动文件：1F专属迁移脚本、`data/default-workspace.json`；若共享柜体已经支持子件，只做数据绑定。
- 验收测试：2D对象树和3D实例均能选中/追溯上柜；06机位中上柜不被冰箱错误吞没；对象同步测试通过。

### P1-02 厨房推拉门与西侧柜尾仅余约34mm，现有校核提示侵入门区186mm

- 分类：真实节点风险 / 现场待复尺
- 影响对象：`D-1F-004`、`furn-kitchen-u-left-run`
- 证据：西侧柜段到y=3016，南墙/门洞线在y=3050；门洞宽2298mm覆盖整面厨房开口。现有门区校核提示柜体侵入约186mm。
- 建议修法：按最终双移门轨道、边框、拉手和收口型材深化柜尾；必要时缩短柜段或做窄封板，保证门扇、轨道检修和柜门均可使用。
- 预计改动文件：1F专属迁移脚本、厨房/门节点详图、`data/default-workspace.json`。
- 验收测试：门扇开合、轨道检修、柜门/抽屉开启三种状态无碰撞。

### P1-03 客卫淋浴宽度安装余量过小，北窗又位于淋浴内

- 分类：现场待复尺 / 施工节点风险
- 影响对象：`furn-bath-shower-001`、`WIN-1F-002`、`ROOM-1F-003`
- 证据：1814mm房宽内放1780mm淋浴，仅余34mm；房间来源容差为80mm。北窗是1200mm推拉窗，窗台1200mm，直接处于淋浴湿区。
- 建议修法：玻璃隔断按完成面实测下单，不锁死1780成品尺寸；补窗台反坡、型材防水、玻璃安全与开窗操作方案。
- 预计改动文件：1F卫浴深化数据、设备选型表、`data/default-workspace.json`。
- 验收测试：完成面最小宽度下仍可安装；窗扇开启、花洒喷淋和玻璃隔断互不冲突。

### P1-04 客卫门开启语义需要最终确认

- 分类：数据语义不确定 / 现场待确认
- 影响对象：`D-1F-005`、`furn-bath-vanity-001`
- 证据：数据写为 `openDirection=rightIn`，但宿主墙 `W-1F-009` 的线方向使当前2D/3D开启法线落到客厅侧；若实际要向客卫内开，则会进入台盆一侧操作区。当前写实图显示门扇向客厅侧开启，但未形成文字冻结决策。
- 建议修法：主任务明确“向客厅外开、向客卫内开或移门”三者之一，再按门框完成面复核900mm净宽和台盆净距；不要只改枚举名不看墙向量。
- 预计改动文件：1F专属迁移脚本、`data/default-workspace.json`。
- 验收测试：2D开启弧、3D门扇、文字说明一致；门扇与台盆、马桶及客厅通道无碰撞。

### P1-05 卧室床尾净距约520mm

### P1-08 双壁龛数据已收敛，但04写实图隐藏了模型中的相邻楼梯边界

- 影响对象：`furn-living-fireplace-south-001`、交付图03/04、内部04机位
- 证据：媒体墙2500mm绑定2650mm的 `W-1F-013`，上下各约75mm余量；当前3D 04可在媒体墙北端看到楼梯，写实图04则补成连续空白墙。双壁龛本体正确，但空间边界被效果图美化。
- 建议修法：保留双壁龛尺寸；通过真实机位裁切或构图避开楼梯，不应在写实阶段虚构连续墙。
- 预计改动文件：1F摄影机数据、十机位产物；无需改媒体墙variant。
- 验收测试：模型预览与写实图在媒体墙两端的墙体/楼梯可见性一致。

### P2-01 双壁龛“活跃数据”已收敛，2D符号与历史归档仍可能造成误读

- 分类：版本治理 / 视觉可审计性
- 影响对象：历史产物、2D顶视符号、媒体墙版本说明
- 证据：当前工作区中 `dualNicheMediaWall`仅有1个活跃引用，`floatingNicheMediaWall`、`singleNiche`和“单壁龛”均为0；当前3D与最终03/04均显示双壁龛。旧artifact/manifests仍保留单壁龛历史版本；2D顶视符号对单/双壁龛使用同一 `planShape=floating`，平面上不能直接辨认版本。
- 建议修法：不删除历史产物；在当前交付索引中明确“仅v15为当前”，并为2D对象标签或符号增加双壁龛识别信息。
- 预计改动文件：当前artifact README/交付索引、1F平面表现配置；底层variant无需修改。
- 验收测试：从当前交付入口不能误点旧版；2D对象属性明确显示 `dualNicheMediaWall`。

### P2-02 衣帽架贴边触发“越界”属于边界判定假阳性

- 分类：校验器问题，不是本层真实几何冲突
- 影响对象：`module-1f-wardrobe-001`、家具放置校验
- 证据：衣帽架东边界x=3897与房间东墙x=3897严格相等，几何上是贴墙；通用校验把边界点判为不在polygon内，报告2/4角点越界并跨到客厅。
- 建议修法：本轮不改共享校验器；由主任务决定是否在公共层加入墙面贴合容差，或在1F对象中采用明确墙锚语义避免误报。
- 预计改动文件：如判定为公共缺陷则为共享校验测试/实现；如采用楼层数据规避则为1F迁移脚本。不得静默挪动衣帽架破坏897mm净距。
- 验收测试：贴宿主墙边界不报越界，真实穿墙仍报错。

## 4. 双壁龛收敛专项结论

### 已收敛

- 活跃1F数据：`furn-living-fireplace-south-001.render3d.variantId=dualNicheMediaWall`。
- 3D实现：当前模型04显示左右双壁龛。
- 写实交付：v15的03和04均为左右双壁龛。
- 自动测试：`scripts/test-furniture-variants.mjs`已锁定 `dualNicheMediaWall`，本轮复跑通过。

### 未完全收敛

- 2D平面符号不能区分单/双壁龛，只能从对象属性确认。
- 旧artifact和旧manifest保留单壁龛历史记录，若没有当前交付索引，人工浏览时仍可能误选。
- 04写实图对媒体墙相邻楼梯/墙端做了美化隐藏，属于空间可见性未收敛，不是variant回退。

结论：双壁龛的活跃模型身份已收敛；2D可读性、归档治理和机位空间边界仍需P1/P2收口。

## 7. 建议实施顺序

1. 先解决餐桌/水吧与冰箱通道两项几何P0，冻结餐桌展开方向、桌心、水吧长度/位置和冰箱SKU。
2. 再做水吧与客卫的现场复尺和机电/防水深化，明确客卫门向、淋浴完成面尺寸及淋浴内窗节点。
3. 用单一1F迁移更新对象坐标、状态包络、吊柜子件和依附点位；随后同步餐桌吊灯，不先改单独灯位。
4. 完成毫米级校验后再调整01/08/10及04摄影机，先输出无UI的模型预览，确认可见对象关系。
5. 最后重渲染十机位，更新当前交付索引并保留历史档案但标注非当前版本。

## 8. 三个最关键风险

1. **餐桌扩容当前不可用**：日常闭合已经碰水吧，2400×1200展开更无餐椅与通道空间。
2. **厨房冰箱段不满足900mm**：当前仅约755–770mm，冰箱开门和抽屉操作会进一步压缩。
3. **湿作业不能落地**：2400mm水吧排水、客卫防水/坡向/窗台节点均未形成施工路径，后期返工成本高。
